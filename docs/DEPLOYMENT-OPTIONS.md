# MCP 배포 선택지

사내 전용 Redmine MCP 서버를 어떻게 배포할 것인가. 각 선택지가 실제로 청구하는
비용을 정리한 결정 노트다.

- **대상**: 192.168.71.103 (기존 평문 서버 3000번 포트)
- **상태**: 미결. 자체 서명 방식으로 한 차례 배포했다가 전부 롤백함
- **기존 서버**: 3000 정상 가동 중, 손대지 않음

---

## 1. 문제

Claude Code는 OAuth 토큰 교환을 **TLS 위에서만** 수행한다. 루프백
(`localhost` / `127.0.0.1` / `::1`)만 예외다.

```
Refusing to send credentials to non-https token endpoint
'http://192.168.71.103:3000/token'.
```

요구가 네트워크 경계가 아니라 **클라이언트 정책**에서 나오기 때문에, "사내망이니
평문으로 충분하다"가 통하지 않는다. 현행 서버는 SDK의 HTTPS 가드를
`MCP_DANGEROUSLY_ALLOW_INSECURE_ISSUER_URL=true`로 끈 상태다. 서버 측 방어를 끈
결과 실패 지점이 클라이언트로 밀렸을 뿐, 문제가 사라진 게 아니다.

`teams-mcp`(3001)도 같은 설정으로 떠 있어 동일하게 로그인이 안 될 것이다.

---

## 2. 근본 갈림길은 인증서가 아니라 transport다

지금까지의 논의는 전부 "HTTP transport를 쓴다"는 전제 위에 있었다. 인증서, DNS,
nginx, 포트 — 이 모두가 **HTTP transport를 지탱하기 위한 부속물**이다.

이 서버는 stdio transport도 지원한다. stdio를 쓰면 위 문제 전체가 사라진다.
OAuth가 없으니 issuer도 없고, issuer가 없으니 TLS도 인증서도 DNS도 nginx도 없다.

```
stdio  →  각 PC에서 MCP 서버 실행  →  https://space.ncurity.com  (공인 인증서)
HTTP   →  192.168.71.103:8443      →  인증서 · DNS · nginx · OAuth · 세션 관리
```

**먼저 transport를 정하고, HTTP를 택한 경우에만 인증서를 고민하면 된다.**

## 3. 선택지 S — stdio

각 사용자 PC에서 MCP 서버를 직접 실행하고, 자기 Redmine API 키로 인증한다.
서버를 운영하지 않는다.

패키지는 npm의 `@gmlee-ncurity/mcp-server-redmine`이다. 다만 **현재 레지스트리에
올라가 있는 최신은 1.0.2**이고(beta 태그는 1.0.8-beta.0), 소스의 1.3.0은 아직
배포 전이다. 아래 예시처럼 버전을 핀으로 박으려면 **1.3.0을 먼저 배포해야 한다.**

### 플러그인으로 배포하는 법

플러그인의 `.mcp.json`:

```json
{
  "mcpServers": {
    "redmine": {
      "command": "npx",
      "args": ["-y", "@gmlee-ncurity/mcp-server-redmine@1.3.0"],
      "env": {
        "REDMINE_URL": "https://space.ncurity.com",
        "REDMINE_API_KEY": "${user_config.redmine_api_key}"
      }
    }
  }
}
```

`plugin.json`:

```json
{
  "userConfig": {
    "redmine_api_key": {
      "type": "string",
      "title": "Redmine API 키",
      "description": "space.ncurity.com 개인 설정에서 발급받은 API 키",
      "sensitive": true,
      "required": true
    }
  }
}
```

`sensitive: true`이므로 입력이 마스킹되고, 값은 `settings.json`이 아니라
**시스템 키체인**(또는 `~/.claude/.credentials.json`)에 저장된다. 값은 플러그인을
설치·활성화할 때 **설정 대화상자로 입력받는다.**

사용자 입장에서는 **플러그인 설치 → API 키 입력. 끝이다.**
셸 프로파일 편집도, Claude Code 재시작도, 인증서 배포도 없다.

### stdio가 없애는 것

| 없어지는 것 | 이유 |
|---|---|
| 인증서 · DNS · nginx | OAuth issuer가 없으니 TLS 요구 자체가 없다 |
| 포트 충돌 (443, 3000–3002) | 서버를 띄우지 않는다 |
| 세션 누수 | HTTP transport 전용 문제다 |
| 기존 서버 폐기 이행 | 옮길 서버가 없다 |
| 클라이언트 재시작 | `NODE_EXTRA_CA_CERTS`를 안 쓴다 |

### 덤으로 얻는 것 두 가지

**API 키가 분산 보관된다.** HTTP 방식에서는 전 사용자의 Redmine API 키가
192.168.71.103의 `oauth-store.json` 한 파일에 모인다. 서버가 털리면 전원의 키가
함께 털린다. stdio는 각자의 키체인에 남는다.

**LAN 밖에서도 된다.** `space.ncurity.com`은 공인 IP(211.177.120.91)로 뜬다.
반면 HTTP 방식은 사설 IP라 사내망이나 VPN 안에서만 닿는다. 재택이나 클라우드
세션에서는 stdio만 동작한다.

### 대가

- **각 PC가 Redmine에 직접 접근**한다. 중앙에서 감사·차단할 지점이 없다.
- **버전 관리가 느슨해진다.** 위 예시는 `@1.3.0`으로 핀을 박았다. `-y` 뒤에
  버전을 빼면 매번 최신을 끌어오므로, 의도치 않은 업데이트를 피하려면 핀을 유지하고
  올릴 때 플러그인을 갱신한다.
- **각 PC에 Node와 npm 접근**이 필요하다. Claude Code를 쓰는 환경이면 대개 충족된다.
- **npm 레지스트리 의존**이 생긴다. 이게 걸리면 플러그인에 패키지를 동봉하고
  `command: "node"`, `args: ["${CLAUDE_PLUGIN_ROOT}/server/dist/index.js"]`로 바꾼다.

### stdio를 못 쓰는 경우

- 사용자 PC에서 Redmine 직접 접근을 정책상 막아야 할 때
- 중앙에서 접근 이력을 남기거나 즉시 차단해야 할 때
- 사용자가 Node를 실행할 수 없는 환경일 때

**이 중 해당하는 게 없다면 아래 4~5장은 읽을 필요가 없다.**

## 4. HTTP를 택했다면 — 제약 사슬

"클라이언트에서 아무 설정도 안 하고 싶다"는 요구는 아래 사슬을 통째로 끌고 온다.
각 인증서 선택지는 이 사슬을 어디서 끊느냐로 갈린다.

```
01  클라이언트 설정 0을 원한다
      ↓                          ← A · B 는 여기서 끊는다 (설정을 감수)
02  공인 CA 인증서라야 한다
      ↓
03  공인 CA는 사설 IP에 발급 못 한다   (CA/B Forum 금지)
      ↓
04  그래서 이름이 필요하다
      ↓
05  이름 해석 = DNS가 필요하다      ← C · D 는 끝까지 가서 DNS를 놓는다
```

### 재시작은 어떤 수를 써도 못 없앤다

`NODE_EXTRA_CA_CERTS`는 Node가 **기동 시점에만** 읽는다. 실행 중에
`process.env`로 넣으면 무시된다(실측: `DEPTH_ZERO_SELF_SIGNED_CERT`).
플러그인 훅으로도, `settings.json`의 `env`로도 우회할 수 없다.

사설 인증서를 쓰는 한(A·B) 사용자는 Claude Code를 한 번 재시작해야 하며, 이 비용은
신규 입사자마다 반복된다. **stdio의 `userConfig` 방식에는 이 문제가 없다** —
API 키는 Claude Code가 서버를 띄울 때 전달하는 값이라 기동 시점 제약을 받지 않는다.

## 5. HTTP를 택했다면 — 인증서 다섯 갈래

| | S · stdio | A · 자체 서명 | B · 내부 CA | C · 기존 와일드카드 | D · Let's Encrypt | E · SSH 터널 |
|---|---|---|---|---|---|---|
| **클라이언트 초기 작업** | API 키 입력 | CA 설치 + 재시작 | CA 설치 + 재시작 | 없음 | 없음 | 매번 터널 실행 |
| **인증서 교체 시** | 해당 없음 | 전 클라이언트 재배포 | 영향 없음 | 영향 없음 | 영향 없음 | 해당 없음 |
| **DNS 필요** | 불필요 | 불필요 | 불필요 | 내부 A 레코드 | 내부 A + 공인 TXT | 불필요 |
| **와일드카드 키 반출** | 없음 | 없음 | 없음 | 이 서버로 복사 | 없음 | 없음 |
| **갱신** | 없음 | 10년 | 루트 10년 | 연 1회 (기존 절차 편승) | 90일, 자동화 불가 | 없음 |
| **서버 추가 비용** | 항목 하나 추가 | 서버마다 배포 | 루트만 신뢰하면 끝 | 와일드카드가 덮음 | 이름마다 발급 | 터널마다 포트 |
| **LAN 밖 접근** | 가능 | 불가 | 불가 | 불가 | 불가 | SSH 되면 가능 |
| **평가** | **추천** | B의 하위호환 | HTTP 중 추천 | 조건부 최선 | 불가 | 임시책 |

### A — 자체 서명 리프

SAN에 IP를 담은 자체 서명 인증서. 한 차례 배포해 **끝까지 동작하는 것을 확인했다**
(전 디스커버리 엔드포인트 https, curl·Node 모두 검증 통과).

문제는 B와 클라이언트 비용이 똑같은데 얻는 게 적다는 점이다. 인증서가 곧 신뢰
앵커라 재발급이 전 클라이언트에 전파된다. **B를 고를 수 있다면 A를 고를 이유가 없다.**

### B — 내부 CA

루트 CA를 하나 만들어 클라이언트에 한 번만 신뢰시키고, 서버 인증서는 그 루트에서
발급한다. 클라이언트 초기 비용은 A와 동일한데, 이후 서버 인증서를 자유롭게
갈아끼울 수 있다. `teams-mcp`까지 얹을 계획이라면 차이가 더 벌어진다.

약점은 루트 키 관리 책임이 생긴다는 것. 사내 CA가 이미 있다면 이 부담이 사라진다.

### C — 기존 `*.ncurity.com` 와일드카드 재사용

Sectigo 발급 와일드카드가 이미 있다. 공인 CA라 **클라이언트 작업이 0**이다.
운영상으로는 HTTP 방식 중 가장 편하다.

대가는 두 가지다. 내부 DNS A 레코드 하나, 그리고 와일드카드 개인키를 이 서버에
두는 것. 서버가 털리면 `*.ncurity.com` 전체가 영향권에 들어간다.

DNS 레코드 자체는 외부 노출과 무관하다. 사설 IP를 가리키는 레코드는 외부에서
라우팅이 불가능하고, 내부 DNS에만 두면 공인 DNS에서 조회되지도 않는다.

만료는 2026-12-04. 공인 인증서 수명은 업계 전체가 줄이는 방향이라 이후 재발급은
더 짧게 끊길 전망이다.

### D — Let's Encrypt DNS-01 (불가)

원리상으로는 가장 좋다. 공인 인증서를 이 서버에서 직접 발급하므로 와일드카드 키
반출 없이 클라이언트 작업 0을 얻는다.

그런데 `ncurity.com`의 네임서버가 **가비아**이고, certbot 공식 DNS 플러그인에
가비아가 없다. 자동화가 안 되면 90일마다 사람이 TXT 레코드를 손으로 넣어야 하고,
한 번 놓치면 전 사용자가 동시에 인증 실패한다. **자동화 없는 90일 갱신은 자체
서명보다 명백히 나쁘다.**

우회로는 `_acme-challenge`를 자동화 가능한 곳으로 CNAME 위임하는 방식이다.
가비아에 CNAME 한 번만 수동으로 넣으면 그 뒤는 무인이지만, 별도 인스턴스를
운영해야 한다. MCP 서버 하나 때문에 치를 비용은 아니다.

### E — SSH 터널 · 루프백 예외 (임시책)

issuer를 `http://127.0.0.1:3000`으로 두고 각자 SSH 터널로 접속한다. 루프백은 TLS
요구에서 면제되므로 인증서가 필요 없다. 토큰은 터널 안에서만 평문이라 보안상
허용 범위지만, 전원이 매번 터널을 띄우고 로컬 포트도 고정해야 한다.

## 6. 권고

**stdio(S)를 권한다.** 중앙 서버가 필요한 이유가 명확하지 않다면, 인증서·DNS·
nginx·OAuth·세션 관리를 전부 없애고 사용자 작업도 API 키 입력 하나로 줄일 수 있다.
API 키가 분산 보관되고 LAN 밖에서도 동작하는 것은 덤이다.

HTTP가 필요한 이유가 있다면 — 중앙 감사, 접근 차단, 또는 사용자 PC의 Redmine 직접
접근 금지 — 그때는 다음 한 문장으로 갈린다.

> **와일드카드 개인키를 192.168.71.103에 두는 것을 정책이 허용하는가?**

- **허용한다면 C.** 클라이언트 작업이 영구히 0이고, 갱신은 기존 연 1회 절차에 편승한다.
- **허용하지 않는다면 B.** 클라이언트가 루트 CA를 한 번 설치하고 재시작하면, 이후
  서버 인증서 교체는 클라이언트와 무관해진다.
- **A는 고르지 않는다.** 같은 값에 더 적게 준다.

사용자 수가 늘수록 C의 우위가 커지고(B의 "설치 + 재시작"은 인원에 비례해 누적된다),
서버 수가 늘수록 B와 C의 차이는 줄어든다.

---

## 7. 결정에 필요한데 확인되지 않은 것

1. **중앙 서버가 필요한 이유가 있는가** — 감사·차단·직접 접근 금지 같은 요구가
   없다면 S로 끝난다. 4~5장 전체가 불필요해진다.
2. **와일드카드 개인키를 이 서버에 둘 수 있는가** — C와 B를 가르는 유일한 질문.
3. **내부 DNS 레코드 추가에 절차가 필요한가** — 번거롭다면 C의 매력이 줄고, 각 PC의
   hosts 파일로 대체하면 B와 손이 비슷해진다.
4. **사내 CA가 이미 운영 중인가** — 있다면 B의 루트 키 관리 부담이 사라진다.
5. **사용자가 몇 명이고 얼마나 늘어날 예정인가** — B의 클라이언트 비용은 인원에
   비례해 누적된다.

## 8. 실측으로 확인한 것

추정이 아니라 이번 작업에서 직접 확인한 사실이다. 어느 선택지를 고르든 다시 검증할
필요가 없다.

| 확인한 것 | 근거 |
|---|---|
| 현행 서버는 SDK의 HTTPS 가드를 끈 상태 | 기존 `docker-compose.yml`에 `MCP_DANGEROUSLY_ALLOW_INSECURE_ISSUER_URL=true` |
| `NODE_EXTRA_CA_CERTS`는 런타임 설정이 무시됨 | `process.env` 할당 후 fetch → `DEPTH_ZERO_SELF_SIGNED_CERT` |
| 패키지가 npm에 존재함 | `@gmlee-ncurity/mcp-server-redmine` · latest 1.0.2 · beta 1.0.8-beta.0 · 소스는 1.3.0 (미배포) |
| 플러그인이 설치 시점에 민감 값을 받을 수 있음 | `userConfig` + `sensitive: true` → 키체인 저장, `${user_config.KEY}`로 참조 |
| 플러그인에 설치 시점 훅은 없음 | postinstall 없음. `SessionStart`가 유일한 대체재 |
| 443을 쓸 수 없음 | `devel-dockerhub`(443→5000)가 `devel.ncurion.com` 자체 인증서로 직접 종단 |
| 호스트에 nginx 없음, 3000–3002 모두 점유 | 3000 redmine-mcp · 3001 teams-mcp · 3002 device-tracker |
| nginx 컨테이너 + 8443 구성이 동작함 | 대상 호스트에서 `nginx -t` 통과, 전 엔드포인트 https 확인 |
| SSE는 프록시 버퍼링을 꺼야 함 | `proxy_buffering off` · `proxy_cache off` · `Connection ''` · `chunked_transfer_encoding off` |
| DNS는 가비아, certbot 공식 플러그인 없음 | `ns1.gabia.co.kr` · `ns.gabia.net` · `ns.gabia.co.kr` |
| 와일드카드가 존재하고 mcp 서브도메인을 덮음 | `CN=*.ncurity.com` · Sectigo · notAfter 2026-12-04 |
| bind mount 설정은 reload로 반영 안 됨 | scp·git pull이 새 inode 생성 → 컨테이너 재생성 필요 |
| `teams-mcp`도 동일하게 망가져 있음 | `TEAMS_BASE_URL=http://192.168.71.103:3001` + `INSECURE_ISSUER_URL=true` |
| 기존 서버의 세션 누수가 진행 중 | `/health` `sessions` 9121 |

## 9. 결정과 무관하게 남는 것

**세션 누수 수정**은 `develop`에 반영돼 원격에 올라가 있다. 유휴 세션 회수
(`MCP_SESSION_TTL`, 기본 30분)와 만료 세션에 대한 404 응답이 추가됐고, 테스트
167개가 통과한다. HTTP를 택한다면 신규 스택은 이 코드로 빌드해야 누수를 안고
시작하지 않는다. stdio를 택하면 애초에 해당 없다.

**배포 구성**은 브랜치에 보존돼 있다. nginx 컨테이너 + 8443 + SSE 설정, 클라이언트
CA 설치 스크립트, 플러그인 `SessionStart` 훅까지 검증을 마친 상태다.

- `feat/tls-deployment` — 와일드카드 + 8443
- `feat/tls-selfsigned` — 자체 서명 IP 인증서
- `feat/tls-client-install` — CA 설치 스크립트 + 플러그인 훅

**남은 별건**으로 `teams-mcp`가 있다. HTTP로 간다면 같은 nginx에 포트 하나만 더
얹으면 되고, stdio로 간다면 그쪽도 같은 방식으로 옮기는 편이 일관적이다.
